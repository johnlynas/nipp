# Units Table (RLS-Enforced) Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Add an org-scoped `Units` table (1:M from `Organization`) modeling the properties an organization manages, with PostgreSQL RLS as a live, CI-tested second line of defense — integrated into every existing invariant (policy-catalog golden, app-layer scoping drift guard, DB-layer isolation suite).

**Architecture:** The repo enforces two isolation layers over *every* org-scoped table: (1) **DB layer** — Postgres RLS policies keyed on the context GUC `app.current_org_id`, live-enforced for the non-owner app role `nipp_app`; (2) **App layer** — the `TENANT_SCOPED_MODELS` list in `lib/tenant-extension-core.ts`, which force-injects the org column into every Prisma op and is drift-guarded by a test that parses `prisma/schema.prisma`. A new table that joins the catalog must ship with: schema model + migration, an RLS policy in the established default shape, the app-layer list entry, fixture rows for org A/B, an entry in the DB-layer isolation spec, and a regenerated `policy-catalog.golden`. Missing any one of these breaks a CI check.

**Tech Stack:** Node 22, Next.js 15, Prisma 6 (PostgreSQL provider), Postgres 16, Vitest, plain-SQL hand-written RLS migration (repo precedent).

## Context / verified facts

- Schema header invariant (`prisma/schema.prisma:1-36`): every org-scoped model carries a required org column + `@@index` on it, and MUST be in `TENANT_SCOPED_MODELS` (drift-guarded by `tests/unit/tenant-db-hardening.test.ts`, which parses the schema live — so **adding the model fails that test until this plan's Phase 2 patch lands**).
- RLS catalog shape for tables whose org column is named `orgId` (Member/Invitation/SentInvitation, `prisma/migrations/20260919093000_rls_complete_policies/migration.sql:86-107`) — **Units uses this exact shape** since the user-specified org column is `orgId`.
- Policy-catalog golden: `tests/isolation/database/policy-catalog.golden` must byte-match live `pg_policies`; regenerate only via `scripts/rls-gen-policy-golden.ts` (never hand-edit).
- `tests/isolation/database/migrations-ownership.spec.ts:64-77` asserts the exact RLS-enabled table list — currently **18 tables**; becomes 19.
- DB-layer fixture: `tests/isolation/database/rls-fixture.ts::seedFixture` seeds deterministic rows per org for every org-scoped table; `tests/isolation/database/rls-org-scoped.spec.ts` iterates an `ORG_TABLES` map and auto-generates visibility + WITH-CHECK probe tests from it.
- App-layer scoping: `lib/tenant-db.ts` resolves models via camelCase (`tenantDb.units`); the org column name comes from `orgFieldFor()` in `lib/tenant-extension-core.ts:65-67`, currently a hardcoded `Member ? 'orgId' : 'organizationId'`.
- Dev DB state is **unverified today** (local Postgres was not reachable at planning time: port 5432 refused). Phase 3 starts with an explicit migration-state check.
- Repo commit convention (per RLS plan execution logs): implementers leave commits to the user — treat every "Commit" step as *optional, per user direction*.
- `CalendarEvent.propertyId` (`prisma/schema.prisma:617`) is a pre-existing nullable placeholder for property association — **out of scope**; wiring it to `Units` is a follow-up.

**Naming decisions (flagged where they deviate):**
- Table/model name `Units`, PK field `unitId`, org column `orgId` — exactly as specified by the user. Deviates from repo convention (singular models, `organizationId`) only to honor the request; `orgId` follows the BetterAuth-model precedent (Member/Invitation/SentInvitation).
- Enum values must be `'House' | 'Apartment' | 'Other'` in the DB. Prisma maps enum member names 1:1 to Postgres labels and has no per-member mapping, so the Prisma enum uses mixed-case members (`Haus…`) — a deliberate, commented deviation from the repo's SCREAMING_CASE enum style. See Task 1A note.

## Phase 1 — Schema

### Task 1A: Add `UnitType` enum + `Units` model to the Prisma schema

**Objective:** Define the table in `prisma/schema.prisma` so the generated client and migration reflect it.

**Files:**
- Modify: `prisma/schema.prisma` (enums section ~line 47-109; new model after `CalendarEvent` (~line 627), before the Job Scheduler section; `Organization` model back-reference at ~line 230)

**Step 1:** Add the enum in the Enums section:

```prisma
/**
 * Unit types. NOTE: mixed-case members are intentional — Prisma maps member
 * names verbatim to Postgres enum labels, and the required labels are
 * 'House' / 'Apartment' / 'Other'.
 */
enum UnitType {
  House
  Apartment
  Other
}
```

**Step 2:** Add the model (convention: `cuid()` PK, `createdAt`/`updatedAt`, cascade to Organization, index on org column):

```prisma
/**
 * Units — The properties managed by an organization (1:M from Organization).
 * Org column is `orgId` (BetterAuth-named-column precedent, like Member);
 * RLS policy rls_units_isolated is keyed on it (see migrations …_units_rls_policy).
 */
model Units {
  unitId   String   @id @default(cuid())
  orgId    String   // Organization this unit belongs to — the RLS column
  owner    String   // Name of the unit owner
  address  String   // Street address of the unit
  postCode String   // Post code of the unit
  rented   Boolean  @default(false) // Is the property rented out?
  type     UnitType @default(Apartment)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  organization Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)

  @@index([orgId]) // Tenant-scoped queries (RLS + app-layer scoping)
}
```

**Step 3:** Add the back-reference in `Organization` (after `calendarEvents`, ~line 230):

```prisma
  units                Units[]      // Properties managed by this organization
```

**Step 4:** Validate + regenerate client:
Run: `npx prisma validate && npx prisma generate`
Expected: both succeed, exit 0.

> **Conformity note (open question):** if strict SCREAMING_CASE enum style is preferred over the user-specified DB labels, swap to `enum UnitType { HOUSE APARTMENT OTHER }` and document the resulting labels `'HOUSE'/'APARTMENT'/'OTHER'`. Default for this plan: literal user spec (`'House'/'Apartment'/'Other'`).

### Task 3B: Hand-write the RLS policy migration (repo precedent: separate policy migration)

**Objective:** `Units` joins the RLS catalog in the exact default shape for `orgId` tables; `nipp_app` gets its grants.

**Files:**
- Create: `prisma/migrations/20261014150000_units_rls_policy/migration.sql` (pick a timestamp later than `_add_units`)

**Step 1:** Full file content:

```sql
-- ============================================================
-- RLS policy for Units — default org-scoped shape on the "orgId" column
-- (identical to Member/Invitation/SentInvitation; rls_complete_policies §2).
-- Fail-closed: empty GUC context matches no row.
-- ============================================================

-- Defensive grant (ALTER DEFAULT PRIVILEGES in 20260919035439_rls_roles already
-- covers owner-created tables; kept explicit so the fresh-chain fixture is
-- self-evident). Idempotent.
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE "Units" TO nipp_app;

ALTER TABLE "Units" ENABLE ROW LEVEL SECURITY;
CREATE POLICY rls_units_isolated ON "Units"
  USING ("orgId"::text = current_setting('app.current_org_id', true)
         OR NULLIF(current_setting('app.is_platform_admin', true), '')::int = 1)
  WITH CHECK ("orgId"::text = current_setting('app.current_org_id', true));
```

**Step 2:** Apply only the new migration:
Run: `npx prisma migrate deploy`
Expected: applies exactly `20261014150000_units_rls_policy`.

**Step 3:** Verify RLS is live + policy exists:
Run: `psql "$DATABASE_URL" -c "\d+ Units"` and `psql "$DATABASE_URL" -tAc "SELECT policyname, cmd FROM pg_policies WHERE tablename='Units'"`
Expected:rowsecurity enabled; one row `rls_units_isolated | ALL`.

## Risks, tradeoffs, open questions

1. **Enum label casing** — mixed-case Prisma members (`House/Apartment/Other`) deviate from repo SCREAMING_CASE style to satisfy the exact DB-label requirement. Decision recorded in Task 1A; switch is a one-line change (pre-migration only).
2. **`orgId` vs `organizationId`** — honors user spec; requires the `ORG_ID_FIELD_MODELS` generalization (done in Phase 2). If convention-compliance wins later, it's a column-rename migration + policy regeneration — cheap now, expensive with data.
3. **Dev DB migration state unknown** at planning time (Postgres was down). Task 3A step 1 gates on `_prisma_migrations`; the no-chain fallback (`migrate deploy` first) is documented. If `prisma migrate dev` reports unexpected drift, do NOT use `--reset` — stop and reconcile manually.
4. **No API/UI in scope** — table + isolation only. Follow-ups (separate plans): REST routes under `app/api/organizations/[orgId]/units/*` using `tenantDb.units`, wiring `CalendarEvent.propertyId → Units.unitId` foreign key, and reusing the already-seeded `properties:*` permission keys (`lib/permissions/property.ts`).
5. Commit granularity follows repo convention (user commits); each phase boundary is a natural commit point if desired.
