# Interactive Organization Chart — Implementation Proposal

**Goal:** A responsive, interactive org chart derived from live database data (Organization → Team → TeamMember → User/Member/Role/Permission), with a right-hand slide-in panel (same interaction as the Calendar page) where an org admin picks which organization's chart to edit, and the admin's left sidebar gains a new menu entry — exactly like the Calendar entry.

**Status:** Proposed

---

## 1. Motivation

- Members and admins currently have no visual way to see the org's hierarchy who-reports-to-whom across teams.
- The Calendar page (app/dashboard/admin/calendar/page.tsx + components/calendar/CalendarSidebar.tsx) already establishes the exact interaction pattern the user wants: full-bleed page, right-hand dark (#1B2A4A) slide-in sidebar, typeable org combobox, super-admin `?org=` switcher via `/api/admin/organizations/list`.
- All required data already exists in the schema — no new business tables are needed:
  - Organization → Team (1:N, organizationId)
  - Team → TeamMember (join table, userId)
  - User (global) + Member (org membership, role)
  - Role / RolePermission / Permission (RBAC, org-scoped)
  - MemberRole (member → assigned roles)

## 2. Current context / assumptions

- Chart renders as a read-derived tree:
  Level 0: organization.
  Level 1: teams (ordered by name; org root node also lists members with NO team).
  Level 2 (optional toggle): team members, each showing user name/email, member role (from MemberRole), and permission summary (role-permission counts, not raw permission keys in the node).
- "Edit" is bounded: in v1 the panel exposes (a) the org switcher, (b) per-node actions that navigate to the existing admin management pages (users, teams, roles), and optionally (c) inline move-member-between-teams using the existing `/api/organizations/[orgId]/teams` endpoints. No new mutation endpoints beyond what exists.
- Permissions drive both visibility and editability:
  - View the chart for your own org: any member (mirrors calendar event access — membership check).
  - Edit / switch org: tenant admin (BetterAuth org role `admin`) in own org, or super admin (existing `requireSuperAdmin` + `/api/admin/organizations/list` pattern from app/api/admin/organizations/list/route.ts).
  - A `org-chart` permission (`org-chart:read`) will be added to the global permission catalog via seed (isDefault: true) so it can be role-gated like `calendar:read` (see prisma/seed.ts:67).
- Tenant isolation is non-negotiable (see schema header tenant-isolation requirement): the read API must verify membership for non-super-admin callers, same pattern as app/api/organizations/[orgId]/teams/route.ts.
- Styling must match the calendar: dark sidebar #1B2A4A, accent #F5A623, collapsed-width pattern (w-16 / w-80), lucide-react icons, Tailwind (no new UI libraries for the tree — hand-rolled CSS fl/grid, or a single small dependency if chosen; recommendation: no new dependency, hand-rolled responsive tree with collapsible levels, zoom buttons, and drag-to-reorder only later).

## 3. Scope

### In scope (v1)
1. GET data endpoint returning the full org tree JSON in one call:
   `GET /api/organizations/[orgId]/org-chart`
   Returns: `{ organization, teams: [{ id, name, members: [{ userId, name, email, image, memberRoles: [{name, permissions: [keys]}], memberRole }] }], unassigned: [...] }`
2. Org chart page + route: `app/dashboard/admin/org-chart/page.tsx`
   - Client component, mirrors app/dashboard/admin/calendar/page.tsx (active org from /api/auth/me, localStorage fallback `nipp-active-org-id`, `?org=` super-admin override).
   - Full-bleed layout (no top header bar, like the calendar's `isCalendarPage` treatment in app/dashboard/admin/layout.tsx:116-127).
3. Right slide-in panel `components/org-chart/OrgChartSidebar.tsx`
   - Mirrors CalendarSidebar.tsx: collapsed w-16 / expanded w-80, typeable org combobox fed by `/api/admin/organizations/list` (super admin only; regular admins see their own org fixed, same as calendar), and a "Members" quick list (click a member → opens their existing view page).
   - Edit affordances when the user has edit rights (tenant admin or super admin): per-node "Manage" buttons linking to `/admin/organization/[orgId]/members`, `/admin/organization/[orgId]/teams`, `/admin/organization/[orgId]/roles`; and a "Move member" action wired to existing team members endpoints.
4. Interactive tree `components/org-chart/OrgChart.tsx`
   - Expand/collapse per node, zoom in/out buttons + reset, pan (mouse drag of canvas), node click opens detail popup (user info + roles + permission summary), responsive: horizontal-scroll/zoom on desktop, vertical stacked variant on mobile (max-width breakpoint), keyboard accessible (tab through nodes, enter to expand).
5. Left sidebar nav entry
   - Add `{ href: '/dashboard/admin/org-chart', label: 'Org Chart', icon: Network }` to navItems in app/dashboard/admin/layout.tsx:11-22 and extend the `isCalendarPage` full-bleed check to include the org-chart path (layout.tsx:28, 116, 125).
6. Seed update: add `org-chart:read` (and optionally `org-chart:update`) to prisma/seed.ts permission catalog, grant to tenant admin role during bootstrap/seed (mirror calendar:read grants).
7. Tests:
   - Unit: tree-shaping utility (rows → tree JSON), client component render tests (jsdom, mirrors tests/unit patterns).
   - Integration: org-chart API membership/permission gating — member can read own org; non-member 403; tenant admin 200; super admin 200 for any orgId; org-switch endpoint only super admin.
   - Isolation: cross-tenant read attempt (org A user requesting org B chart → 403), following tests/isolation/application/team-isolation.test.ts pattern.
   - E2E (Playwright, optional for v1): page loads for super admin, sidebar open/close, org switch, node expand/collapse, zoom.

### Out of scope (defer)
- Drag-and-drop re-parenting of members/teams inside the tree UI (endpoints exist; UI deferred to v2).
- Reporting-line ("reportsTo") field — the schema has no manager relation; hierarchy is org→team→member. If reporting lines are wanted, that's a separate schema-change proposal.
- Custom permission display on every node (show role names; permission keys on demand in the detail popup).
- Print/PDF export.
- Non-super-admin cross-org browsing (regular admins only see their own org).

## 4. Detailed design

### 4.1 Data shape & endpoint

`GET /api/organizations/[orgId]/org-chart`

Authorization (in order):
1. `requireSuperAdmin` passes → proceed (any orgId).
2. Else membership check `globalDb.member.findFirst({ where: { userId, orgId } })` → 403 if missing.
3. Else permission check via `lib/permissions/resolver` (or existing authorization helper used by calendar routes) for `org-chart:read` → 403 if missing. (Regular members pass if membership + permission; keep v1 simple: membership is sufficient for reading their own org's chart, matching calendar access; the permission key is added for future gating.)

Response (single query in `lib/global-db`):
```
organization: { id, name, description }
teams: [{ id, slug, name, description, members: ChartMember }]
unassigned: ChartMember[]        // members with no team membership
ChartMember = {
  userId, name, email, image,           // from User
  memberRole: string,                     // from Member (better-auth role)
  assignedRoles: [{ id, name, permissionCount, permissions: [key] }]  // from MemberRole -> Role -> RolePermission -> Permission
  teams: [teamSlug]                      // which teams the member belongs to
}
```

Implementation notes:
- One Prisma call: `organization.findUnique` with `teams` (include `members: { user, ... }` via TeamMember), plus `members` for the org level (Member → user, memberRoles). Compute `unassigned` = org members whose userId is not in any TeamMember for the org.
- Put the shaping in `lib/org-chart.ts` (pure function tree-shaper, unit-testable without DB).
- Cache: none in v1 (data is small; calendar uses similar patterns). Redis/hybrid cache is a v2 consideration.

### 4.2 Page (`app/dashboard/admin/org-chart/page.tsx`)

Clone the structure of app/dashboard/admin/calendar/page.tsx:
- Init: `/api/auth/me` → `activeOrganizationId` + name; localStorage fallback `nipp-active-org-id`; super-admin `?org=` override via `/api/admin/organizations/list`.
- Render `<OrgChart organizationId={orgId} organizationName={...} sidebarOpen onSidebarToggle onOrganizationSelected onMemberClick />`.
- Loading + "No organization selected" states, same styles (color #1B2A4A text) as calendar page.

### 4.3 Sidebar (`components/org-chart/OrgChartSidebar.tsx`)

Mirror CalendarSidebar.tsx exactly (copy the combobox behaviour: focus-to-search, outside-click close, Enter picks first match, Escape resets):
- Collapsed: `w-16`, icon-only, expand button (same toggle button styles).
- Expanded: `w-80`, sections:
  1. Organization combobox (super admin: all orgs from `/api/admin/organizations/list`; tenant admin: single fixed value with no combobox, showing own org name — matches calendar behaviour).
  2. "Manage" section (only when user has edit rights for the displayed org): links
     - Organization settings → `/admin/organizations/[orgId]/settings`
     - Members → `/admin/organizations/[orgId]/members`
     - Teams → `/admin/organizations/[orgId]/members` (teams managed from members/teams pages — use existing routes)
     - Roles → `/admin/organizations/[orgId]/roles`
  3. "Teams" list: each team with member count; click to scroll/expand that team's subtree in the chart (dispatch custom event or callback to OrgChart).
  4. "Unassigned members" list (if any): click opens member detail in the tree, or the existing user view page.
- Styling tokens identical to CalendarSidebar: bg #1B2A4A, borders #24355c/#3a4f7a, accent #F5A623.

Edit-rights detection: super admin (`me` from /api/auth/me doesn't expose role — use `/api/auth/me` response or existing pattern: super admin is identified by access to `/api/admin/organizations/list`; tenant admin by membership.role === 'admin' — the endpoint can add `canEdit: boolean` to the org-chart GET, or a lightweight `/api/auth/me` extension. Recommendation: org-chart GET returns `viewerCanEdit` computed server-side from membership role + super-admin status.)

### 4.4 Tree (`components/org-chart/OrgChart.tsx`)

- Props: `tree: ChartTree` (from API), `canEdit: boolean`, `onMemberClick(member)`, `onTeamClick(teamId)` (to sync with sidebar).
- Layout: CSS grid/absolute-positioned tree (org root centered top; teams in a row; members fanned under each team). Pure CSS + mouse-wheel zoom (transform: scale) + drag-to-pan of the inner canvas. No external tree library in v1.
- Interactions:
  - Click node → expand/collapse (team members collapsible per team; top level always visible).
  - Double-click or "details" button on member node → detail panel (reuse a Modal from components/dashboard/Modal.tsx): name, email, member role, assigned roles with expandable permission list, team memberships.
  - Zoom in / out / reset buttons, top-right overlay.
  - Pan by dragging background; touch-friendly (single-finger pan, pinch later).
  - Responsive: below `md` breakpoint, switch to a vertical indented list layout (accordion of teams → members) — this is what "responsive" delivers for phones; desktop gets the spatial tree.
- Accessibility: nodes are buttons with aria-expanded/aria-controls; tree container role="tree"; keyboard: Tab focus, Enter/Space toggle, ArrowRight expand, ArrowLeft collapse.

app/dashboard/admin/layout.tsx:

- Full-bleed: replace `isCalendarPage` with `isFullScreenPage = isCalendarPage || isOrgChartPage` (used at lines 116 and 125).

## 7. Risks / Decisions

Decisions (settled with the requester):
1. **Chart depth:** org → team → member is sufficient for v1. No reporting lines; if they become a requirement, that's a separate schema-change proposal (`Team.leaderId` or `Member.managingMemberId`).
2. **Team–member display:** 1:1 in v1 — each member renders under exactly one team (no "also in" badge). The API resolves any multi-membership data to the primary membership (earliest `createdAt`, ties broken by team name). Schema/index-level enforcement is deferred.
3. **Dashboard audience:** v1 = super-admin dashboard only (`RequireSuperAdmin` layout, matching calendar). Tenant access to the org chart (org-admin self-service page, e.g. `/dashboard/owner/org-chart`) waits until v2.

Remaining tradeoffs:
- Large orgs (hundreds of members): collapse-by-default per team keeps DOM small; virtualization deferred (YAGNI).
- CSRF: v1 is GET-only — no state-changing requests. Existing POST/PUT team-members endpoints already enforce `isSameSiteRequest`; v2 inline editing reuses them.
- Permission seed change requires re-seed or bootstrap for existing DBs: document in proposal tasks (run `npm run db:seed` in dev; production rollout via the existing permission-bootstrap path — verify `lib/org-bootstrap.ts` picks up new default permissions on next bootstrap).

## 8. Acceptance criteria

- Super admin sees "Org Chart" in left sidebar; page loads their active org's chart.
- Right slide-in panel (same look/feel as calendar sidebar) opens and closes; org combobox switches tenants for super admin (URL ?org= preserved across refresh).
- Tree renders organization → teams → members from live DB data, each member under exactly one team (1:1 v1 rule); roles & permissions visible per member (detail popup).
- Collapse/expand, zoom, pan work; mobile shows vertical accordion layout.
- Non-members get 403 hitting the API (verified by isolation test); non-super-admins cannot reach the page (RequireSuperAdmin layout) — tenant access is v2.
- Super admin sees edit affordances for every organization.
- `npm run test`, `npm run lint`, `npm run type-check`, `npm run build` all pass.
