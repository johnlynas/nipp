# Contractor Data Model Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Add a global (non-org-scoped, RLS-exempt) `contractors` table + `ContractorType` enum to the Prisma schema so external contractors can be shared by all organizations in the portal.

**Architecture:** New Prisma model with no `organizationId` column — it joins the documented EXEMPT set of global tables (like `Resource`/`ResourceRole`). Two isolation layers are both intentionally NOT touched: no DB RLS policy, and no app-layer entry in `TENANT_SCOPED_MODELS`. The repo's drift guards (unit test that parses the schema, RLS golden catalog) prove nothing else needs to change. A standard additive migration ships the DDL; docs documenting the exemption are updated per the project rule "any new model must ship with either an org column + policy, or an explicit documented exemption" (`documents/rls-complete-implementation.md` line 285).

**Tech Stack:** Prisma (PrismaClient, migrations), PostgreSQL, Vitest (unit drift guard), Next.js repo conventions.

---

## Context & assumptions (from codebase inspection)

- Schema: `prisma/schema.prisma`. All org-scoped models carry `organizationId` + a relation + `@@index`; the header comment (lines 1–36) enumerates the EXEMPT global models — a new exempt model MUST be added there.
- Recent precedent to mirror exactly: the `Units` model (`prisma/schema.prisma:648-663`) and its two migrations `prisma/migrations/20261014143000_add_units/` + `prisma/migrations/20261014150000_units_rls_policy/`. Contractors differs only by omitting the org column, FK, RLS migration (none of them).
- **Drift guard 1 (unit):** `tests/unit/tenant-db-hardening.test.ts` parses `schema.prisma` for models with a *required* `organizationId/orgId` String field and asserts that set equals `TENANT_SCOPED_MODELS` (`lib/tenant-extension-core.ts:35`). Because `contractors` has no org column, it is excluded from the parsed set — **no code change needed, this test must stay green.**
- **Drift guard 2 (DB):** `tests/isolation/database/migrations-ownership.spec.ts` asserts (a) RLS enabled on exactly 19 named tables (contractors not among them → no change) and (b) that a hardcoded list of exempt tables (`User,Session,Account,Resource,ResourceRole`) has NO RLS — contractors is not in that literal list → no change. `tests/isolation/database/policy-catalog.golden` lists live policies; **zero new policies are created, so the golden file stays untouched.** Do NOT run `scripts/rls-gen-policy-golden.ts` expecting changes — it should produce an identical file (that is itself a useful verification).
- **App-role access:** `prisma/migrations/20260919035439_rls_roles/migration.sql:39` sets `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO nipp_app`, and all migrations run as the owner role — so a new table gets the grants automatically. No explicit GRANT is required (the Units migration included one for parity; optionally include an idempotent-style comment in the file but no statement needed).
- Enum naming: Prisma enums are SCREAMING_SNAKE_CASE, e.g. `CalendarEventType.MAINTENANCE` (`prisma/schema.prisma:66-74`). The requested "GAS ENGINEER" etc. become `GAS_ENGINEER`. The spec lists `PLUMBER` twice — de-duplicate to one value.
- Model name is `Contractors` (title case — user-confirmed rename from lowercase `contractors`) following repo convention (`Units`, `Organization`). Client access: `prisma.contractors`, column/PK: `contractorId`.

```prisma
// ============================================================
// Contractors (Global shared directory — NOT org-scoped)
// ============================================================

/**
 * contractors — external contractor records shared by all organizations.
 * Globally accessible on purpose: any organization can use any contractor,
 * so there is NO organizationId column, NO app-layer tenant scoping
 * (absent from TENANT_SCOPED_MODELS), and NO RLS policy (RLS-exempt table,
 * documented in SECURITY.md Appendix B). Grants for nipp_app come from the
 * ALTER DEFAULT PRIVILEGES set in 20260919035439_rls_roles.
 */
model Contractors {
  contractorId  String         @id @default(cuid()) // Auto-generated primary key
  companyName   String         // Contractor's company name
  name          String         // Contractor's name
  email         String         // Contractor contact email
  phone         String         // Contractor contact phone number
  address       String         // Contractor business address
  postCode      String         // Contractor business address post code
  type          ContractorType @default(OTHER) // Business type; description clarifies when OTHER
  description   String?        // Optional; primarily used for type=OTHER, usable by all types
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt
}
```

## Risks, tradeoffs, and open questions

1. ~~**`type` has no default**~~ — RESOLVED: `type` carries `@default(OTHER)` (user-confirmed during execution).
2. **No uniqueness on `email`/`phone`** — duplicates are allowed, so two rows can describe the same contractor from different orgs' data entry. If global-directory semantics demand a single canonical row per email, add `@unique` (migration would then carry a unique index — regenerate in Task 3). Flagged as an open question because it changes the DDL.
3. ~~**Field naming `postcode` vs repo precedent `postCode`**~~ — RESOLVED: renamed to `postCode` (user-confirmed) for consistency with `Units.postCode`; applied pre-migration, so no data migration needed.
4. ~~**Model name casing**~~ — RESOLVED: model renamed to `Contractors` (title case, repo convention) per user direction; applied pre-migration.
5. **Exemption blast radius** — with no RLS and (initially) no route-level gating planned, any authenticated app-layer code that hits `contractors` sees all contractors. That is the intended design (shared directory), but future CRUD routes MUST gate writes at the route boundary (auth + permission check) since the DB will not stop anything. The `lib/permissions/*` scaffolding for a Contractor role (`lib/roles/contractor.ts`) exists for the future feature proposal; nothing in this plan wires up routes — model-only scope, per YAGNI.
6. **No org↔contractor junction** — knowing which organization engaged which contractor is not captured here (spec doesn't ask for it). If needed later, a junction `OrgContractor` with RLS would be the correct follow-up proposal.
7. Dev-DB drift: if the dev database was last touched via `db push`, `migrate dev` may report drift — resolve per Task 3 Step 1 (do not reset without confirmation).
