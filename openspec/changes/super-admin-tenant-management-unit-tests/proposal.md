# Proposal: Super Admin Tenant Management — Unit Tests

## Intent

Write comprehensive unit tests for all code generated by the `super-admin-tenant-management` OpenSpec proposal. This includes unit tests for:

1. **API route handlers** — structural verification and mocked handler tests
2. **UI form components** — render, interaction, and submission behavior

These tests verify correctness of the super admin tenant management feature without requiring a running database or server, enabling fast feedback during development.

## References & Foundational Rules

This proposal builds upon and must strictly adhere to the rules established in:

- **`project-initialization`**: Core architecture, testing infrastructure (Vitest 4.x), version pinning.
- **`super-admin-tenant-management`**: The feature this proposal tests — API endpoints, UI pages, and components.
- **`auth-and-rbac`**: RBAC engine, permission catalog, `requireSuperAdmin()` guard pattern.
- **`super-admin-org-mgmt`**: Existing super admin patterns, `<RequireSuperAdmin>` component.

**Mandatory Rules Enforced:**
- **Test-Driven Completeness**: Every new API route handler and UI component must have corresponding unit tests.
- **Version Pinning**: Tests must run with Vitest 4.x on Node.js 22 LTS.
- **No Real Dependencies**: All tests must use mocks — no real database, no running server.
- **Strict Property NI Design System Compliance**: UI component tests verify correct use of Navy (#1B2A4A) and Amber (#F5A623) design tokens.

## Non-Regression Requirements

This proposal MUST NOT break any existing tests:
- All existing unit tests in `tests/unit/` must continue to pass.
- Existing API route structural tests (e.g., `admin-permissions.test.ts`) must continue to pass.
- Existing component tests (e.g., `RequireSuperAdmin.test.tsx`) must continue to pass.

## Scope

**In Scope:**
1. **API Route Structural Tests** — Verify that each new API route:
   - Exports the correct HTTP method handlers (GET, POST, PATCH, DELETE)
   - Uses `requireSuperAdmin()` guard on all handlers
   - Validates request body parameters
   - Returns correct HTTP status codes (200, 201, 400, 403, 404, 409, 500, 503)
   - Uses `globalDb` for cross-org lookups and `tenantDb` within `runWithTenant()` for scoped operations

2. **API Route Handler Tests (Mocked)** — Verify handler logic with mocked Prisma:
   - `GET /api/admin/organizations/[orgId]/members` — List members, org not found
   - `POST /api/admin/organizations/[orgId]/members` — Add member, duplicate check
   - `PATCH /api/admin/organizations/[orgId]/members/[memberId]` — Update role, member not found
   - `DELETE /api/admin/organizations/[orgId]/members/[memberId]` — Remove member, member not found
   - `GET /api/admin/organizations/[orgId]/roles` — List roles, org not found
   - `POST /api/admin/organizations/[orgId]/roles` — Create role, duplicate check
   - `PATCH /api/admin/organizations/[orgId]/roles/[roleId]` — Update role, role not found
   - `DELETE /api/admin/organizations/[orgId]/roles/[roleId]` — Delete role, in-use check
   - `GET /api/admin/organizations/[orgId]/permissions` — Fetch permissions grid
   - `PATCH /api/admin/organizations/[orgId]/permissions` — Assign/revoke permissions
   - `PATCH /api/admin/organizations/[orgId]/settings` — Update settings, state machine validation

3. **UI Component Tests** — Verify form components with Testing Library:
   - `TenantMemberForm` — Render, submit with valid/invalid data, cancel button
   - `TenantRoleForm` — Render, submit with valid/invalid data, cancel button

4. **State Machine Tests** — Extend existing `org-state-machine.test.ts` to cover the settings route transitions:
   - PENDING → ACTIVE, ACTIVE ↔ SUSPENDED, ACTIVE → ARCHIVED (terminal)
   - Invalid transitions return 400

**Out of Scope:**
- Integration tests (covered in separate proposal)
- E2E/Playwright tests (covered in isolation-testing-infrastructure proposal)
- Database-layer RLS tests (deferred)

## Testing Strategy

### API Route Structural Tests
Read source files and verify:
- Correct exports (GET, POST, PATCH, DELETE functions)
- `requireSuperAdmin()` guard present on all handlers
- Request body validation (email required, role required, etc.)
- Correct HTTP status codes in error responses

### API Route Handler Tests (Mocked)
Use Vitest's `vi.mock()` to mock:
- `@/lib/global-db` — Mock Prisma organization queries
- `@/lib/tenant-db` — Mock Prisma member/role/permission queries
- `@/lib/tenant-context` — Mock `runWithTenant()` to execute callback directly
- `@/lib/require-super-admin` — Mock auth guard (authorized/unauthorized)
- `@/lib/audit-log` — Mock audit log recording

Test each handler for:
- Happy path (successful operation)
- Auth failure (403 when not super admin)
- Not found (404 for missing org/member/role)
- Validation errors (400 for missing required fields)
- Conflict (409 for duplicate member/role/slug)
- Database unavailable (503 when DB connection fails)

### UI Component Tests
Use `@testing-library/react` with jsdom environment:
- Render component with props
- Verify form fields are present and labeled correctly
- Test submit behavior (calls onSubmit, resets form)
- Test cancel button (calls onCancel)
- Verify disabled state during submission
- Verify design tokens (Navy headers, Amber buttons)

### State Machine Tests
Extend existing tests to cover the settings route's `VALID_TRANSITIONS`:
- All valid transitions from super-admin-org-mgmt proposal
- Invalid transitions (ARCHIVED terminal, PENDING→SUSPENDED skip)

## Acceptance Criteria

- [ ] All 12 new API routes have structural tests verifying correct exports and guards
- [ ] All 12 new API routes have mocked handler tests covering happy path + error cases
- [ ] `TenantMemberForm` component has tests for render, submit, cancel, and disabled states
- [ ] `TenantRoleForm` component has tests for render, submit, cancel, and disabled states
- [ ] State machine tests cover all transitions defined in the settings route
- [ ] All new tests pass with `npx vitest run` (zero failures)
- [ ] No existing tests are broken by new additions
- [ ] Tests run in under 10 seconds total

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Mocking complexity — Prisma has many nested relations | Medium | Start with simple mocks, add complexity incrementally; use `vi.mock()` at module level |
| Tests become brittle due to implementation details | Medium | Focus on behavior (status codes, response shapes) rather than internal logic |
| UI tests require jsdom setup | Low | Use `@vitest-environment jsdom` directive at top of test files |
| Test duplication with integration tests | Low | Unit tests verify logic in isolation; integration tests verify full flow — different concerns |
